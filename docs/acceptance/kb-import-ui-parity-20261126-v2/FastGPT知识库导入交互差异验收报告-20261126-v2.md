## 5. 问题明细

### P0-01 QA 段落参数没有传给后端

**问题 ID：BE-PARAM-QA-PAYLOAD-001**

项目在“问答对提取 → 自定义 → 按段落”中展示了：

- 模型识别段落。
- 最大段落深度。
- 最大分块大小。

但实际预览请求的 `chunking` 对象只有：

```json
{
  "trainingType": "qa",
  "chunkSettingMode": "custom",
  "chunkSplitMode": "paragraph",
  "chunkTriggerMinSize": 1000,
  "chunkSize": 1000,
  "overlap": 100
}
```

缺少 `paragraphChunkAIMode`、`paragraphChunkDeep` 和 `paragraphChunkMinSize`。用户修改“模型识别段落”或“最大段落深度”后，预览和最终导入不会使用该设置。

项目根因：

- `packages/web/src/product/import-workspace.tsx:310` 只有在 `chunkSplitMode === 'paragraph' && trainingType === 'chunk'` 时才加入段落参数。
- `packages/web/src/product/import-workspace.tsx:2721` 起仍对 QA 模式渲染同一组段落控件。

FastGPT：

- 同一 `CollectionChunkForm` 同时服务 chunk 与 QA。
- `CollectionChunkForm.tsx:416-478` 的段落参数不依赖 `trainingType`。
- `Import/commonProgress/DataProcess.tsx:48` 使用同一表单进入预览和上传。

**业务影响：** QA 页面的关键控件是静默空操作，用户无法控制 QA 拆分粒度。  
**修复建议：** QA `paragraph` 模式也必须发送段落参数；前后端测试应断言实际请求和最终 chunk policy 都包含这些字段。  
**复验标准：** 修改三项段落参数后，请求体和预览分块结果均发生变化。

### P0-02 QA 引导词及每块问答数量与 FastGPT 不一致

**问题 ID：BE-QA-PROMPT-001**

项目当前标签为 `QA Prompt`，默认没有显示所谓“QA 拆分引导词”，自定义弹窗内容只有通用占位文字。后端 `packages/qa/src/prompt.ts:12` 使用的是自研模板：

```text
你是知识库问答对生成助手。
请阅读给定文本，生成尽可能多的高质量问答对。
...
```

FastGPT 标签为 `QA 拆分引导词`，默认模板见 `packages/global/core/ai/prompt/agent.ts:2-8`：

```text
<Context></Context> 标记中是一段文本，学习和分析它，并整理学习成果：
- 提出问题并给出每个问题的答案。
- 答案需详细完整，尽可能保留原文描述，可以适当扩展答案描述。
- 答案可以包含普通文字、链接、代码、表格、公示、媒体链接等 Markdown 元素。
- 最多提出 50 个问题。
- 生成的问题和答案和源文本语言相同。
```

FastGPT 自定义弹窗还展示不可自定义的响应格式和 `<Context>{{text}}</Context>` 包装：

```text
请按以下格式整理学习成果:
<Context>
文本
</Context>
Q1: 问题。
A1: 答案。
...
```

此外项目 `packages/service/src/modules/knowledge/application/s5-qa-pipeline.ts:142` 把 `maxQaPerChunk` 固定为 `5`，而 FastGPT 默认引导词要求最多 50 个问题。即使只替换界面默认文案，项目仍最多保留 5 个问答对。

**业务影响：** QA 生成指令、上下文边界、输出格式和最大结果数都不同，不能达到 FastGPT 的业务效果。  
**修复建议：** UI 改名为“QA 拆分引导词”；默认显示 FastGPT 引导文本；把可编辑引导词与不可编辑输出格式分开组装；默认模板使用 `<Context>` 包装；每块上限与模板声明的 50 对齐，或明确通过独立可配置项实现。  
**复验标准：** 页面默认文案、弹窗只读格式、模型实际收到的 prompt、`maxQaPerChunk` 四项一致并通过模型请求捕获测试。

### P1-01 四步页面整体比例和容器模型不一致

**问题 ID：UI-IMPORT-LAYOUT-001**

项目给所有四步统一套用 `1120px` 最大宽度和带边框、阴影、圆角的内部主卡片：

- `fastgpt-product.css:2733-2745`：`kb2-import-body max-width: 1120px`。
- `fastgpt-product.css:2749`：内部再次形成主面板。
- 实测参数页仍为 `1070px`。

FastGPT：

- `Import/index.tsx:44` 页面使用 `px=36px、py=20px`。
- 步骤条 `Import/Context.tsx:279` 单独限制 `900px`。
- 参数页 `commonProgress/DataProcess.tsx:48` 单独限制 `640px`。
- 上传、预览、确认区使用页面可用内容宽度。

项目根因不是图片比例，而是给不同业务步骤错误复用了同一最大宽度。

**修复建议：** 容器按步骤拆开：步骤条 `width:100%; max-width:900px`；参数页 `width:100%; max-width:640px`；文件、预览、确认页使用导入内容区全宽；外层采用 FastGPT 的 `36px` 水平、`20px` 垂直内边距，并移除非 FastGPT 的内部卡片层级。

### P1-02 参数设置页仍显示“上传完成”文件条

**问题 ID：UI-IMPORT-UPLOADROW-001**

- 项目：进入第 2 步后仍显示“上传完成”文件名、大小和进度条，实测数量为 1。
- FastGPT：进入参数设置后上传列表消失，实测数量为 0。

项目根因：

- `import-workspace.tsx:581` 使用 `showFormStep = directSelection ? step <= 1 : step === 1`。
- 结果第 0、1 步都渲染同一套本地文件表单。

FastGPT `diffSource/FileLocal.tsx` 将 `SelectFile` 和 `DataProcess` 严格按 `activeStep` 条件切换。

**修复建议：** 第 0 步只渲染文件选择/上传；第 1 步只渲染参数设置。上传文件数据保留在状态中，但不重复显示上传行。

### P1-03 参数控件的说明、范围和步进不可发现

**问题 ID：UI-PARAM-GUIDANCE-001**

项目当前：

- 模型识别段落下拉只有“禁用 / 自动 / 强制”，无说明，且“强制”文案与 FastGPT“强制处理”不同。
- 最大段落深度只有数字框，没有 `1~8` 范围提示，也没有 `step=1`。
- 最大分块大小、按长度分块的分块大小无范围提示或步进。
- 分块条件值允许从 `1` 开始，而 FastGPT 从 `100` 开始且步进 `100`。

FastGPT 源码和实机：

- 自动：“当文本内容不含 Markdown 标题时，启用模型识别。”
- 禁用：“强制禁用模型自动识别段落”。
- 强制处理：“强制使用模型自动识别段落，并忽略原文本的段落（如有）”。
- 最大段落深度 `min=1、max=8、step=1`。
- 分块大小使用 `minChunkSize` 至模型上限，并通过 Tooltip 显示“范围：min~max”。
- 分块条件值 `min=100、max=100000、step=100`。

**修复建议：** 保留下拉但为三项增加说明；数字输入补 `step`、可见范围或 Tooltip；修正“强制处理”文案和分块条件边界。

2. 1 个换行符
3. 2 个换行符
4. 句号
5. 感叹号
6. 问号
7. 分号

源码位置：

- `CollectionChunkForm.tsx:521-548`：选择器及“自定义”条件输入。

**修复建议：** 改为选择器加条件输入；预设内部值与 FastGPT 对齐；继续允许后端解析多个分隔符，但不要让自由文本替代预设入口。

### P1-06 确认上传表有正确字段，但表格布局仍错误

### 已部分修复：索引大小候选值

**问题 ID：UI-PARAM-INDEX-001（部分关闭）**

用户报告项目只有 `64/128/256/512`。当前工作树代码已经改为按绑定 embedding 模型的 `maxToken` 动态过滤：

- `import-workspace.tsx:383-389` 生成候选列表。
- E2E mock 模型上限为 8192 时，项目实际显示 14 项：`64` 到 `8192`。
- FastGPT 当前账号模型上限为 4096，实机显示 10 项：`64` 到 `4096`。

源码规则一致。若真实项目仍只显示 4 项，应检查实际绑定模型的 `limits.maxToken` 是否为 512，而不是把 14 项硬编码进 UI。

**结论：** 当前代码层面已修复“固定 4 项”；真实环境的模型能力元数据仍需复核。
